# 이 문서는 확장시스템의 질문/답변/필터 분류 기준으로 질문/답변 데이터 기준 설계확장을 위한 스케치 문서이다.

좋아. “**데이터로 답을 먼저 만들고 → 그 결과로 정책을 역설계**”를 하려면, 실험 세트(10문항)를 **축(axis) 커버리지 + RDF 활용 + MVP 밖 확장**까지 한 번에 걸리게 설계해야 해.

아래는 바로 실행 가능한 **Answer-first 실험 세트 10문항 + 각 문항별 최소 데이터 요구(무엇을 채워야 답이 나오는지)** 스케치야.

---

# A-1) Answer-first 실험 세트 (10문항) 고정안

## 구성 원칙 (강제)

* **A(단일 정답 이벤트) 4개**: strict만으로 답 가능하게
* **B(REVEALS 근거) 3개**: reveal 없으면 답이 약해지게
* **C(WHY/도미노) 3개**: PRECEDES 체인 없으면 WHY가 붕괴되게
* 축(axis)은 각 문항마다 **주축 1개만**: `PRECEDES / REVEALS / STATE / PRESSURE`

> MVP 밖 확장 반영: `STATE/PRESSURE`는 “relation type 추가”로 가지 말고, **RDF에서 `:revealsAttribute`로 우회(= event_reveal 확장)** 하는 방향으로 실험한다.
> 즉 “상태/압력”은 트리플로는 표현하지만, 런타임은 **strict+PRECEDES+REVEALS**만으로도 답이 나오게 만든다.

---

# A-1-1) 10문항 리스트 + 축 + 템플릿 스케치

아래는 “질문ID(실험용) / 질문 / 주축(axis) / strictFilters(스케치) / 근거 채우기” 순서.

---

## A급(4) 단일 정답 이벤트 (strict만으로 OK)

### T01 첫 제조는 언제?

* **axis**: PRECEDES(정렬축)
* **strictFilters**: `subject=Walter`, `predicateCodeAnyOf=[<COOK 계열 runtime code>]`, `qAnyOf=[cook, meth, RV]`(필요시)
* **필수 데이터**

  * event: predicate_code, episode
  * event_character: Walter INVOLVED(최소)
* **RDF 활용**

  * `(Event) :subject Walter` 또는 `:participant Walter`
  * `(Event) :predicateCode "..."`

### T02 투코를 처음 만난 시점은 언제?

* **axis**: REVEALS(“투코 등장/접점”을 드러내는 사건)
* **strictFilters**: `with=Tuco`, `qAnyOf=[meet, deal, tuco]` + (predicate anchor는 runtime에 맞게)
* **필수 데이터**

  * event_character: Walter/Jesse INVOLVED + Tuco INVOLVED
  * episode
* **RDF 활용**

  * SPARQL optional: `?e :participant Tuco` + `?e :participant Walter|Jesse`

### T03 RV 독성 가스로 무력화한 사건은 언제?

* **axis**: PRECEDES
* **strictFilters**: `subject=Walter`, `qAnyOf=[gas, RV, phosphine, incapacitate]` (predicate anchor 있으면 더 좋음)
* **필수 데이터**

  * 해당 이벤트 1개 + episode
  * involved 인물 2~3명 INVOLVED면 충분
* **RDF 활용**

  * optional: `:revealsAttribute :Attr/chemical=PH3` 같은 힌트 트리플 (없어도 정답은 나오게)

### T04 월터의 첫 살인은 언제/누구?

* **axis**: PRECEDES
* **strictFilters**: `subject=Walter`, `predicateCodeAnyOf=[<KILL 계열 runtime code>]`
* **필수 데이터**

  * event_character role이 INVOLVED뿐이어도 정답은 가능 (누구 죽였냐는 object 있으면 더 좋음)
* **RDF 활용**

  * role이 나중에 들어오면 `(Walter, KILLS, Krazy-8)` 형태로 깔끔해짐

---

## B급(3) REVEALS 근거가 핵심인 질문 (reveal 없으면 “설명”이 빈약해짐)

### T05 스카일러가 의심을 ‘시작’한 사건은 언제이며, 단서(근거)는 뭐였나?

* **axis**: REVEALS
* **strictFilters**: `subject=Skyler` 또는 `target=Walter`, `qAnyOf=[suspicion, lie, disappear]`
  (predicate anchor는 현실 enum에 맞춰서)
* **필수 데이터**

  * answer_event 1개
  * **event_reveal 최소 2개**: `reveal_hint`(예: “밤새 실종”, “이상한 변명” 같은 단서 키)
* **RDF 활용**

  * SPARQL: `?e :revealsAttribute ?attr`로 hint 목록을 뽑아 UI에 근거로 보여주기

### T06 행크 수사가 ‘한 단계 올라간’ 전환 사건은 언제이며, 어떤 단서가 공개됐나?

* **axis**: REVEALS
* **strictFilters**: `subject=Hank`, `qAnyOf=[DEA, clue, Heisenberg, suspect]`
* **필수 데이터**

  * answer_event 1개
  * event_reveal 1~3개 (단서 키워드/아이템)
* **RDF 활용**

  * reveal을 그래프 카드로 묶어 보여주기(“왜 이 전환이냐”)

### T07 거짓말이 ‘더 큰 거짓말’을 낳은 첫 사건은?

* **axis**: STATE (하지만 구현은 revealsAttribute로 우회)
* **strictFilters**: `subject=Walter`, `qAnyOf=[lie, alibi, cover, story]` + predicate anchor optional
* **필수 데이터**

  * answer_event 1개
  * event_reveal 1~2개: `Attr/concealment_level` 같은 상태 힌트(값은 낮/중/높)
* **RDF 활용**

  * `:revealsAttribute :Attr/concealment_level=2` 같은 식으로 “진화”를 시각화 가능

## C급(3) WHY/도미노 (PRECEDES 체인 없으면 WHY가 불완전)

### T08 “왜 월터가 크레이지-8을 죽였나?” (WHY)

* **axis**: PRECEDES
* **strictFilters**: `subject=Walter`, `predicateCodeAnyOf=[<KILL>]`
* **필수 데이터**

  * answer_event 1개 (살해 이벤트)
  * **event_relation PRECEDES 체인 2~3개** (원인 방향)
  * event_reveal 1개(선택): “접시조각 사라짐” 같은 결정적 근거
* **RDF 활용**

  * SPARQL은 optional. 기본은 코드 BFS로 because_chain 생성
  * RDF는 because_chain의 이벤트들을 트리플로 풍부하게 렌더링(설명 UI용)

### T09 “왜 투코 앞에서 폭발 시연을 했나?” (WHY)

* **axis**: PRESSURE (구현은 revealsAttribute로 우회)
* **strictFilters**: `with=Tuco`, `qAnyOf=[fulminate, explosion, prove, threaten]`
* **필수 데이터**

  * answer_event 1개
  * PRECEDES 원인 이벤트 1~2개 (거래 압박/위협)
  * revealsAttribute 1개: `Attr/threat_pressure=high`
* **RDF 활용**

  * 압력(pressure)을 숫자/레벨로 표현해서 “왜”를 직관화 가능

### T10 “월터-제시 관계가 ‘상하/통제’로 바뀐 첫 전환 사건은?” (WHY+진화)

* **axis**: STATE
* **strictFilters**: `subject=Walter`, `with=Jesse`, `qAnyOf=[control, manipulate, threaten, dependency]`
* **필수 데이터**

  * answer_event 1개
  * PRECEDES 체인 1~2개(전환 전 사건)
  * revealsAttribute: `Attr/power_balance=Walter_dominant` (혹은 level 0→1 같은)
* **RDF 활용**

  * 관계 상태를 attribute로 넣어 RDF에서 시각화(“전환점” 설명에 최적)

# A-1-2) 실험 산출물(데이터-대답) 포맷 고정

각 질문에 대해 JSON 스냅샷을 만들자. **정책은 이 결과를 보고 역설계**한다.

```json
{
  "question_id": "T08",
  "axis": "PRECEDES",
  "strict_filters": { "subject": "Walter", "predicateCodeAnyOf": ["KILLS"] },
  "answer_event_id": 1234,
  "because_chain": [1201, 1210, 1234],
  "reveal_hint": ["plate shard missing"],
  "status": "ANSWERED"
}
```

* 핵심은 **answer_event_id가 항상 존재**해야 하고,
* WHY류는 **because_chain이 최소 2개 이상**이어야 한다.

# A-1-3) RDF 활용 정책 (실험에 맞춘 현실적 규칙)

실험 단계에서는 이렇게 하면 깔끔해.

### 기본

* **정답 탐색/판정**: SQL+코드 strict-first
* **근거/표현 강화**: RDF/SPARQL

### SPARQL을 쓰는 곳(실험에서)

* T05~T07: `reveal_hint`를 SPARQL로 “근거 카드 묶음”으로 뽑기
* T08~T10: because_chain은 코드 BFS로 만들고, SPARQL은 “체인 이벤트들의 SPO를 풍부하게 렌더링”할 때만

즉, SPARQL은 “정답 찾기 엔진”이 아니라 “설명/근거 렌더링 엔진”으로 고정.

# A-1-4) 이 실험이 끝나면 자동으로 결정되는 것들(정책 역설계 포인트)

이 10개를 실제 데이터로 답하게 만들고 나면, 아래가 “정답 기반”으로 고정된다:

1. **strictFilters allow-list**
   어떤 키가 실제로 답 생성에 필요했는지(남기고, 나머지 버림)

2. **axis 매핑표(A1)**
   문서가 아니라 “답 생성이 어떤 축을 썼는지”로 주축이 결정됨

3. **WHY 포맷(W1/W2)**
   because_chain이 몇 hop에서 끊기는지, reveal_hint가 몇 개 필요한지 통계로 고정 가능

4. **RDF export 범위**
   reveal이 SPARQL에 필요하면, export에 event_reveal이 반드시 포함돼야 함(아니면 실험 자체가 실패)
