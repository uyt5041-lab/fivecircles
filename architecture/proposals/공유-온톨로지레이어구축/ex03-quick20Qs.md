맞다. 이게 **온톨로지가 위키와 갈라지는 핵심 지점**이다.
아래 질문들은 **문서 단위 위키로는 거의 불가능하거나, 가능해도 수작업 분류 없이는 유지가 안 되는 것들**이고,
**Event + 관계 기반 온톨로지**에서는 “질의”로 바로 풀리는 것들이다.

아래는 **맥락적 카테고라이제이션이 없으면 성립하지 않는 질문 20개**다.

---

## 인물 중심 질의 (Character-centric)

1. **인물 A가 직접 참여한 모든 사건을 시간순으로 보여줘**
2. **인물 A와 인물 B가 함께 등장한 사건만 보여줘**
3. **인물 A와 적대 관계에 있는 인물들을 모두 나열해줘**
4. **인물 A의 소속이 바뀐 사건들만 모아줘**
5. **인물 A가 어떤 사건들을 통해 ‘중요 인물’로 부상했는지 보여줘**
6. **인물 A가 죽거나 퇴장한 이후에도 영향을 미친 사건들만 추려줘**
7. **인물 A가 원인이 된 사건들(간접 포함)을 모두 보여줘**

---

## 사건 중심 질의 (Event-centric)

8. **이 사건에 직접 또는 간접적으로 연관된 인물들을 모두 보여줘**
9. **이 사건의 원인이 된 이전 사건들을 단계별로 정리해줘**
10. **이 사건 이후에 파생된 사건들만 모아줘**
11. **이 사건이 ‘무엇을 드러낸(reveal)’ 사건인지 설명해줘**
12. **같은 유형의 사건들(예: 배신, 전투, 공개)을 모아서 비교해줘**
13. **이 사건과 구조적으로 유사한 사건들을 다른 에피소드에서 찾아줘**

---

## 관계·맥락 질의 (Relation / Context)

14. **인물 A → 사건 X → 인물 B로 이어지는 관계 경로를 보여줘**
15. **인물 C가 참여한 모든 전투 사건만 필터링해서 보여줘**
16. **서로 다른 에피소드지만 동일한 갈등 축에 속한 사건들을 묶어줘**
17. **같은 사건을 서로 다른 인물 관점에서 재구성해줘**
18. **‘정체가 밝혀지는’ 유형의 사건들만 모아서 나열해줘**

---

## 위키로는 특히 힘든 고급 질의

19. **아직 직접 등장하지 않았지만, 이전 사건들로 인해 필연적으로 예고된 사건들은 무엇인가**
20. **특정 인물의 서사가 어떤 사건 카테고리(전투/배신/희생/폭로)에 가장 많이 걸쳐 있는지 분석해줘**

---

## 왜 일반 위키로는 힘드냐 (핵심 요약)

일반 위키는 기본 단위가 이거다:

> **문서 = 사람 기준으로 읽는 설명**

그래서:

* “A에 대해 써 있다”는 건 알 수 있어도
* “A가 참여한 사건들”은 **암묵적**이고
* “관계 경로 / 유형 / 시간 범위”는 **질의 대상이 아님**

반면 온톨로지는:

> **사건 + 관계 + 범위 = 질의 가능한 구조**

이기 때문에,
위 질문들은 **검색(search)** 이 아니라
**그래프 질의(graph query)** 로 바로 풀린다.

---

## 한 문장으로 정리

> 위키는 “설명하기 위한 지식”이고,
> 온톨로지는 “묻고 답하기 위한 지식”이다.

지금 너희가 만들고 있는 구조는
**‘사람이 읽는 위키’ 위에
‘기계가 답하는 질문 레이어’를 얹는 것**이다.

다음으로 이어서 가면 아주 자연스러운 질문은 이거다:

> “그럼 이 질문들을 실제 API로 어떻게 쪼개야 하지?”

## 난이도 기준으로 정렬

 **“이걸 구현 난이도 기준으로 나눈다”**는 건 곧
**MVP 범위 설정 + 로드맵을 만든다는 뜻**이라서 아주 정확한 질문이야.

아래는 **구현 난이도 기준 4단계**로 정리한 결과다.
(기준: 데이터 모델 복잡도 + 쿼리 복잡도 + 추론 필요 여부)

---

# 🟢 Level 1 — 단순 연결 조회 (MVP 1차, 가장 안전)

> **핵심:**
> 단일 테이블 + 직접 연결(`event_character`)
> ❌ 추론 없음 ❌ 다단계 없음

### 질문들

1. 인물 A가 직접 참여한 모든 사건을 시간순으로 보여줘
2. 인물 A와 인물 B가 함께 등장한 사건만 보여줘
3. 인물 C가 참여한 모든 전투(특정 사건 유형)를 보여줘
4. 이 사건에 직접 등장하는 인물들을 모두 보여줘
5. 특정 사건 유형(전투/배신/공개 등)의 이벤트만 모아서 보여줘

### 구현 특징

* JOIN 1~2개
* where + order by
* **Event 정의 + event_character만 있으면 가능**

👉 **무조건 MVP에 들어가야 하는 레벨**

---

# 🟡 Level 2 — 범위·유형 필터링 (MVP 확장, still safe)

> **핵심:**
> Event의 속성(episode range, predicate/type)을 적극 활용
> ❌ 그래프 탐색 없음

### 질문들

6. 인물 A의 소속이 바뀐 사건들만 보여줘
7. 인물 A가 죽거나 퇴장한 사건만 보여줘
8. 같은 유형의 사건들(배신/전투 등)을 모아 비교해줘
9. 특정 에피소드 범위 안에서 발생한 사건들만 보여줘
10. 이 사건이 어떤 유형(카테고리)에 속하는지 알려줘

### 구현 특징

* Event predicate/type 설계가 중요
* episode_start / episode_end 적극 사용
* 여전히 **SQL로 충분히 가능**

👉 **MVP+α (2차 스프린트)에 적합**

---

# 🟠 Level 3 — 관계 기반 탐색 (온톨로지다워지는 지점)

> **핵심:**
> `event_relation`을 타기 시작
> ✔ BFS / hop 개념 등장
> ❌ 자동 추론은 없음

### 질문들

11. 이 사건의 원인이 된 이전 사건들을 보여줘
12. 이 사건 이후에 파생된 사건들을 보여줘
13. 인물 A → 사건 X → 인물 B로 이어지는 관계 경로를 보여줘
14. 인물 A와 관계있는 인물들을 모두 보여줘
15. 인물 A가 원인이 된 사건들을 간접 포함해서 보여줘

### 구현 특징

* BFS or multi-join 필요
* hop 제한 필수
* **너희가 최근 구현한 multi-hop event search가 정확히 이 레벨**

👉 **“이건 온톨로지다”라고 말할 수 있는 최소선**

---

# 🔴 Level 4 — 맥락 추론 / 메타 질의 (MVP 밖, 미래)

> **핵심:**
> 관계를 “해석”해야 함
> ✔ 암묵적 의미 ✔ 구조적 패턴
> ❌ 명시 데이터만으로는 부족

### 질문들

16. 인물 A가 어떤 사건들을 통해 중요 인물로 부상했는지 보여줘
17. 아직 직접 등장하지 않았지만, 필연적으로 예고된 사건들은 무엇인가
18. 같은 사건을 서로 다른 인물 관점에서 재구성해줘
19. 서로 다른 에피소드지만 동일한 갈등 축에 속한 사건들을 묶어줘
20. 특정 인물의 서사가 어떤 사건 카테고리에 가장 많이 걸쳐 있는지 분석해줘

### 구현 특징

* 이벤트 의미 해석 필요
* 가중치 / 빈도 / 패턴 인식
* 사실상 **Reasoning / Analytics 영역**

👉 **연구 주제 / 차기 버전 / 논문감**

---

# 🎯 핵심 결론 (아주 중요)

* **Level 1 + 2**
  → “구조화된 위키”
* **Level 3**
  → “온톨로지 서비스”
* **Level 4**
  → “지식 추론 시스템”

👉 너희 프로젝트의 현재 위치는
**Level 3 입구에 정확히 서 있다.**

> ❌ 지금 스펙에 넣으려고 하면 프로젝트가 망한다

## API 예시


좋아. 순서를 이렇게 가는 게 가장 이해가 빠르다.

1️⃣ **REST / GraphQL이 뭐냐 (개념부터)**
2️⃣ **왜 온톨로지 질의랑 연결되는지**
3️⃣ **아까 뽑은 20개 질문을 실제 API 형태로 바꿔보기**

---

## 1️⃣ REST / GraphQL이 뭐냐 (비유로 딱 정리)

### REST = “정해진 메뉴판에서 주문”

* 서버가 **미리 정해둔 엔드포인트**를 제공
* 클라이언트는 거기서 **고르기만** 함

예:

```
GET /characters/{id}/events
GET /events/{id}/characters
GET /characters/{id}/battles
```

특징:

* 단순함
* 캐시, 디버깅 쉬움
* **질문이 늘어날수록 API가 늘어남**

👉 **MVP에 가장 적합**

---

### GraphQL = “원하는 대로 조합해서 주문”

* 엔드포인트는 보통 하나
* 대신 **질문 구조를 클라이언트가 직접 정의**

예:

```graphql
query {
  character(id: 1) {
    events {
      characters {
        name
      }
    }
  }
}
```

특징:

* 표현력 강함
* 온톨로지 질의에 매우 잘 맞음
* 대신:

  * 러닝커브
  * 보안/쿼리 제한
  * 운영 복잡도 ↑

👉 **지금 단계에서는 과함**

---

### 한 줄 결론

* **REST = “질문을 서버가 설계”**
* **GraphQL = “질문을 사용자가 설계”**

너희는 지금 **질문 유형을 설계 중**이니까
👉 **REST로 충분하고, 오히려 안전**하다.

---

## 2️⃣ 왜 온톨로지 질의랑 연결되냐

온톨로지는 이미 내부적으로 이걸 하고 있다:

* 노드(Event, Character)
* 관계(INVOLVES, PRECEDES, REVEALS)
* 범위(episode_start/end)

REST / GraphQL은 **“이 그래프를 어떻게 밖으로 꺼내느냐”의 문제**일 뿐이다.

즉:

> 온톨로지 = 질문에 답할 수 있는 구조
> API = 그 질문을 밖으로 노출하는 형식

---

## 3️⃣ 아까 20개 질문 → REST API로 변환

아래는 **MVP 기준, REST로 가장 자연스럽게 쪼갠 버전**이다.

---

### 🧍 인물 중심

1. 인물 A가 참여한 모든 사건

```
GET /characters/{id}/events
```

2. 인물 A와 B가 함께 등장한 사건

```
GET /events?characters=A,B
```

3. 인물 A와 적대 관계 인물

```
GET /characters/{id}/related-characters?relation=ENEMY
```

4. 인물 A의 소속 변경 사건

```
GET /characters/{id}/events?type=AFFILIATION_CHANGE
```

5. 인물 A의 중요 전환점 사건

```
GET /characters/{id}/events?tag=TURNING_POINT
```

6. 인물 A 사후에도 영향 준 사건

```
GET /characters/{id}/events?impact=POST_EXIT
```

7. 인물 A가 원인이 된 사건

```
GET /characters/{id}/events?role=CAUSE
```

---

### ⚡ 사건 중심

8. 사건에 연관된 모든 인물

```
GET /events/{id}/characters
```

9. 사건의 원인 사건들

```
GET /events/{id}/causes
```

10. 사건 이후 파생 사건

```
GET /events/{id}/effects
```

11. 사건이 드러낸 정보

```
GET /events/{id}/reveals
```

12. 같은 유형의 사건들

```
GET /events?type=BETRAYAL
```

13. 구조적으로 유사한 사건

```
GET /events/{id}/similar
```

---

### 🔗 관계·맥락

14. A → 사건 → B 관계 경로

```
GET /paths?fromCharacter=A&toCharacter=B
```

15. 인물 C가 참여한 전투

```
GET /characters/{id}/events?category=BATTLE
```

16. 같은 갈등 축 사건

```
GET /events?conflictAxis=X
```

17. 사건을 인물 관점으로 재구성

```
GET /events/{id}/perspectives
```

18. 정체가 밝혀지는 사건들

```
GET /events?relation=REVEALS
```

---

### 🧠 고급 (위키로는 거의 불가)

19. 예고된 사건들

```
GET /events?status=FORESHADOWED
```

20. 인물 서사 통계

```
GET /characters/{id}/event-stats
```

---

## 4️⃣ GraphQL로 하면 어떻게 되느냐 (참고만)

GraphQL이면 위 질문 대부분이 이렇게 **하나로 합쳐진다**:

```graphql
query {
  character(id: 3) {
    events(filter: { type: BATTLE }) {
      episodeStart
      episodeEnd
      characters {
        name
      }
    }
  }
}
```

멋있다.
하지만 **지금은 멋보다 완성이 중요**하다.

---

## 5️⃣ 최종 판단 (지금 단계에서의 정답)

* ✔ 온톨로지 질의는 이미 REST로 충분히 표현 가능
* ✔ 질문 유형이 명확 → REST가 오히려 안전
* ❌ GraphQL은 “질문 폭발”이 생길 때 도입

> **지금은 REST = 설계된 질문 세트**
> **나중에 GraphQL = 자유 질문 모드**

이 순서가 가장 현실적이다.

---

다음으로 이어지는 진짜 중요한 질문은 이거다:

> “이 API들을 프론트에서 직접 다 쓰나,
> 아니면 ‘질문 전용 서비스(QA/Query Service)’로 한 번 더 감싸나?”

이건 **아키텍처 결정 포인트**라, 원하면 바로 이어서 정리해줄게.
