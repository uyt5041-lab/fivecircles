# 이 문서는 프로덕션 질문의 후속질문, 1번의 후속  6가지를 기준으로 질문/답변 데이터 기준 설계확장을 위한 스케치 문서이다.

## 정합성 고정(필수, REVEALS 문서 기준)

- strict 정답 선택은 사실 이벤트(`event`) strict-first만 사용한다.
- `event_reveal`/`reveal_type(HINT|CONFIRM)`는 WHY/근거 강도 표시에만 사용한다.
- strict miss 상태에서 reveal/probe hit만으로 `ANSWERED` 승격을 허용하지 않는다.
- canonical 기준:
  - `fivecircles/architecture/specs/reveals/reveal-evidence-label-policy.md`
  - `fivecircles/architecture/specs/reveals/reveals-classification.md`
  - `fivecircles/architecture/specs/reveals/reveals-routing-mvp-and-v3.md`

맞아. 네가 올린 **후속 #1~#6**는 “도미노처럼 보이지만”, 실제로는 **PRECEDES만으로는 ‘연표’까지만 가능**하고, 너가 원하는 “맥락 커버리지(정당화/익숙해짐/압력/파장/전환점)”는 **다른 축이 같이 있어야** 진짜로 넓어진다.

여기서 핵심은 이거야:

## PRECEDES는 레일이고, 확장 커버리지는 “REVEALS + Attribute(STATE/PRESSURE)”로 먹는다

* **PRECEDES**: 사건의 순서를 만든다 (도미노의 ‘넘어지는 방향’)
* **REVEALS**: 왜 이 사건이 의미 있는지 “근거/단서”를 준다 (도미노의 ‘설명’)
* **STATE/PRESSURE**: “정당화/익숙해짐/위협 증가” 같은 **추상 변화**를 데이터로 잡는다
  단, 이건 굳이 relation type 확장(`CAUSES_STATE`)로 안 가도 돼. 지금 너희 현실(코덱스 리뷰) 고려하면 **event_reveal의 target을 Attribute로 확장**하는 게 가장 싸고 덜 깨짐.

즉, **관계타입은 PRECEDES-only 유지**하면서도, 커버리지 확장은 가능해.

# 1) 후속 #1~#6이 PRECEDES만으로 왜 한계냐 (정확히 어디서 막히냐)

### 후속 #1 “정당화 논리”

* PRECEDES로는 “S1E2 감금 → S1E3 리스트 작성 → 살해”까진 나열 가능
* 하지만 질문의 핵심은 “논리/정당화”라서

  * **‘장단점 리스트’** 같은 *내적 의사결정*,
  * **‘선택이 아니라 생존’ 프레이밍 전환** 같은 *신념 변화*
    를 **사건 요약 텍스트**로만 처리하면, 검색/재사용/검증이 안 돼.

✅ 해결: `event_reveal(Attribute)`로 “정당화 프레임”을 한 번이라도 찍어야 함

---

### 후속 #2 “폭력에 익숙해진 징후”

* PRECEDES는 사건 순서만 말해줌
* “익숙해짐”은 **상태(레벨) 변화**야.
  즉 이 질문은 사실상 “폭력/위협을 도구로 쓰기 시작한 첫 포인트”를 찾는 거고,
  그건 predicate 하나로도 완벽히 안 잡히는 경우가 많음.

✅ 해결: `reveal_attribute: violence_normalization_level` 또는 `intimidation_as_tool=true` 같은 “상태 스탬프” 필요

---

### 후속 #3 “전략적 살인으로 넘어간 외부 압력”

* 여긴 거의 PRECEDES가 아니라 **압력 누적(수사/조직/가족/대체 가능성)** 이야기임
* PRECEDES로 나열하면 “그럴듯한 설명”은 되지만,
  서비스 관점에서는 “압력의 종류/레벨”을 **검색 가능하게** 만들어야 커버리지가 늘어.

✅ 해결: `pressure_tag`(DEA/ORGANIZATION/FAMILY/REPLACEMENT 등) + `pressure_level`을 Attribute로 기록

---

### 후속 #4 “살인을 선택지로 계산”

* 이건 “의사결정 구조화”라서 #1과 동일 계열
  ✅ 해결: `decision_mode=calculated` 같은 Attribute + 근거 reveal

---

### 후속 #5 “2차 파장”

* 이건 PRECEDES보다 **EFFECT(영향 대상)**이 핵심
* 지금 너희 모델은 공식적으로 CAUSE/EFFECT relation을 안 쓰기로 되어 있고(적어도 runtime은 PRECEDES-only), 그러면 “파장”은

  * **(a) 영향을 받은 캐릭터가 등장하는 후속 사건들**을 PRECEDES로 보여주거나
  * **(b) 그 영향 자체를 Attribute로 찍어두는 방식**
    둘 중 하나로 가야 함.

✅ 현실적: (a) PRECEDES + (b) reveal_attribute “impact_scope=family|dea|partner” 같이 가볍게 찍기

---

### 후속 #6 “전환점 3개”

* 이건 사실 “요약/편집” 문제라서, PRECEDES로 전체를 나열하면 뽑을 수는 있는데
* “전환점”을 뽑는 기준이 필요함 (폭력/압력/통제 등)

✅ 해결: 각 전환점 이벤트에 `reveal_attribute: turning_point=true` + 이유 태그(violence/pressure/control)

---

# 2) “확장 커버리지”를 넓히는 데이터 정책 (지금 구현 현실 반영)

너희 코덱스 리뷰에서 이미 걸린 제약들(ROLE/ENUM/PRECEDES-only/export reveal 부재)을 고려해서, **깨지지 않는 확장**은 딱 이거야:

## 정책: 확장 축은 “코드에서”, 증거는 “event_reveal(Attribute)”로

1. **relation type은 그대로 PRECEDES-only**
2. **role은 지금은 INVOLVED가 대부분이어도 OK**
3. 대신 “맥락 축”은 아래처럼 **Attribute 키 10~12개**만 먼저 도입

   * 이건 DB 스키마 크게 안 바꾸고도 가능(= event_reveal을 활용)
4. `reveal_type(HINT|CONFIRM)`는 근거 강도 표시용으로만 사용하고 정답 승격 조건으로 사용하지 않는다.

### 최소 Attribute 키 세트 (후속 1~6 커버용)

* `justification_frame` (e.g., survival / family / necessity)
* `decision_mode` (impulsive / calculated)
* `violence_normalization_level` (0~3)
* `intimidation_as_tool` (true/false)
* `threat_pressure_level` (0~3)
* `threat_pressure_source` (dea / buyer / organization / family)
* `concealment_level` (0~3)
* `impact_scope` (partner / family / dea)
* `turning_point` (true/false)
* `turning_point_reason` (violence / pressure / control)

이 정도면 “정당화/익숙해짐/압력/파장/전환점”이 **검색 가능한 데이터**가 된다.

---

# 3) RDF 활용은 어디서 “확장 커버리지”에 실제로 도움 되나

RDF가 이미 있으면, 여기서 제일 큰 이득은 **정답 찾기**가 아니라 **근거/맥락을 풍부하게 보여주는 것**이야.

* 정답 이벤트: SQL strict-first가 더 안전
* 근거(why): RDF/SPARQL로 “reveal_attribute 묶음”을 예쁘게 뽑아내면 UX가 확 올라감

### 딱 하나 선행 조건

지금 export가 `event_reveal`을 안 내보낸다고 했지?
확장 커버리지의 핵심이 reveal/attribute인데, RDF가 그걸 안 싣고 있으면 RDF 활용은 말뿐이 돼.

✅ 그래서 “확장 커버리지” 관점에서 RDF 작업 1순위는 이거 하나야:

* **RDF export에 `event_reveal`(특히 revealsAttribute) 포함**

# 4) 후속 #1~#6을 “데이터-대답”으로 만들기 위한 최소 입력(실험 계획)

너가 원하는 “데이터 기준으로 답을 만든 뒤 정책 확정”을 하려면,
후속 6개에 대해 **각각 1개의 answer_event + 1~3개의 reveal_attribute + (필요시) PRECEDES 2 hop**만 준비하면 된다.

### #1 정당화 논리

* answer_event: S1E3 살해
* precedes: 감금 → 리스트작성 → 살해 (2 hop)
* reveal_attribute(필수): `justification_frame=survival` + `decision_mode=calculated`

### #2 폭력 익숙해짐 징후

* answer_event: S1E6 폭발 시연 (또는 최초 위협 도구화 이벤트)
* reveal_attribute: `intimidation_as_tool=true`, `violence_normalization_level=1`

### #3 외부 압력 누적

* answer_event: “투코 거래 구조 진입” 같은 전환 이벤트
* reveal_attribute: `threat_pressure_source=buyer`, `threat_pressure_level=2`
* (시즌2 데이터 없으면) status는 NO_DATA로 떨어지게 설계

### #4 살인을 계산하기 시작

* answer_event: 리스트 작성 이벤트
* reveal_attribute: `decision_mode=calculated`

### #5 2차 파장

* answer_event: 살해 직후 “공범 구조 고정”을 보여주는 사건
* reveal_attribute: `impact_scope=partner` (+ optionally family/dea)

### #6 전환점 3개

* answer_event 3개를 미리 “turning_point=true”로 태깅
* reveal_attribute: `turning_point_reason=violence/pressure/control`

이렇게 만들면, PRECEDES만으로는 못 하던 질문들이 **데이터로 ‘정확히’ 답**이 나오고,
그 순간부터 너희 정책(축/템플릿/WHY 포맷)은 “감”이 아니라 “근거”가 생김.

---

# 5) 정리: 확장하려면 뭘 해야 하고, 뭘 안 해야 하냐

### 해야 하는 것

* PRECEDES-only 유지하면서도
* **event_reveal(Attribute)로 STATE/PRESSURE를 최소 키로 기록**
* RDF export에 event_reveal 포함
* 축(axis)은 DB가 아니라 **executor 코드 정책**으로 운용

### 지금 당장 하지 말아야 하는 것

* `CAUSES_STATE/INCREASES_PRESSURE` 같은 relation type 확장(코덱스 리뷰 그대로 런타임 충돌)
* predicate 예시를 enum 밖에서 막 쓰기(드리프트 지옥)
