# 지능형 서비스 사양 v1 (LLM 기반 온톨로지 정제)

> **상태**: 제안됨 / 논의 중
> **역할**: 팀원 C (지능형 로직 및 필터)
> **목표**: 사용자가 입력한 자연어 위키 기여 내용을 구조화된 온톨로지 트리플(이벤트-서술어-인물)로 변환.

---

## 1. 주요 책임

지능형 서비스(Intelligence Service)는 **온톨로지 정제기(Ontology Refiner)**로서 원본 텍스트에 대해 세 가지 핵심 작업을 수행합니다.

### 작업 A: 개체 추출 (involvedCharacterIds)

- **목표**: 텍스트에 언급된 모든 인물을 식별하고 시스템 내부의 `character_id`와 매핑합니다.
- **프로세스**: 정확한 매핑을 위해 LLM 호출 시 해당 드라마의 캐릭터 목록(이름/별칭 및 ID)을 컨텍스트로 제공합니다.

### 작업 B: 서술어 분류 (predicateCode)

- **목표**: 이벤트의 핵심 행동을 미리 정의된 `PredicateCode` Enum 카테고리로 분류합니다.
- **제약**: 그래프의 무결성을 유지하기 위해 반드시 정해진 집합(예: `사망`, `배신`, `만남`) 내에서만 선택합니다.

### 작업 C: 요약 정제 (refinedSummary)

- **목표**: 감정적이거나 비격식체인 원본 내용을 타임라인 노출에 적합한 건조하고 표준화된 요약문으로 재작성합니다.
- **예시**: "와 진짜 미쳤다 A가 자기 친구 B를 배신하다니" -> "인물 A가 동료 B를 배신함"

---

## 2. 아키텍처 및 워크플로우

### 독립 서비스 분리

- 무거운 LLM 처리 로직과 AI 관련 의존성(예: Python/FastAPI)을 핵심 비즈니스 로직(`wiki-service`)으로부터 분리하기 위해 전용 서비스(`intelligence-service`)를 운영합니다.

### 비동기 강화 흐름 (하이브리드 방식)

1. **기여 등록**: 사용자가 위키 팩트를 `wiki-service`에 등록합니다 (실시간).
2. **분석 요청**: `wiki-service`가 메시지 큐 또는 비동기 호출을 통해 `intelligence-service`를 트리거합니다.
3. **초안 생성**: LLM이 "구조 제안(인물, 서술어, 정제된 요약)"을 생성합니다.
4. **사용자 컨펌 (Human-in-the-loop)**: 기여자 또는 검수자에게 알림이 가며, 사용자는 태그 에디터 UI를 통해 AI가 생성한 태그를 확인하거나 수정합니다.

---

## 3. 기술 전략

### ID 매핑 (컨텍스트 주입)

- 잘못된 ID 매핑을 방지하기 위해, 특정 드라마에 대한 분석 요청 시마다 `character-service`에서 최신 캐릭터 목록을 가져와 프롬프트에 포함합니다.
- **프롬프트 예시**: "이 드라마의 인물들: [101: 존 스노우, 102: 대너리스]. 본문: '존이 대너리스를 만났다'. ID를 추출해줘." -> 출력: `[101, 102]`.

### 할루시네이션(Hallucination) 방지 및 확장 전략

- **백엔드**: LLM 응답에 대해 **JSON Schema**를 강제합니다. 정의되지 않은 서술어가 올 경우 `OTHER`를 기본값으로 사용합니다.
- **Semantic OTHER 전략**: LLM이 적절한 Enum 값을 찾지 못한 경우, `predicateCode`는 `OTHER`로 반환하고 `predicateSuggestion` 필드에 원래 의도했던 서술어(예: "KIDNAPS")를 포함하여 전달합니다. 이는 향후 온톨로지 확장 데이터로 활용됩니다.
- **프론트엔드**: AI 제안을 "클릭 가능한 태그 배지" 형태로 렌더링합니다. 사용자는 잘못된 태그를 삭제하거나 DB 검색을 통해 누락된 인물을 수동으로 추가할 수 있습니다.

### Fallback 매커니즘 (AI 호출 불가 시)

1. **규칙 기반 (정규식)**: 텍스트 내 캐릭터 이름 포함 여부를 단순 키워드 매칭으로 검사합니다.
2. **시스템 기본값**: 서술어는 `OTHER`, 관련 인물은 위키 페이지의 주인공 1명으로 기본 설정합니다.
3. **수동 트리거**: 사용자/관리자가 나중에 다시 시도할 수 있도록 "AI 재분석" 버튼을 제공합니다.

## 4. API 인터페이스 (초안)

### `POST /intelligence/refine`

- **요청 (Request)**:
  ```json
  {
    "dramaId": 1,
    "content": "자연어 텍스트 본문",
    "context": {
      "characterList": [{"id": 101, "name": "인물A"}, ...]
    }
  }
  ```
- **응답 (Response)**:
  ```json
  {
    "predicateCode": "BETRAYS",
    "predicateSuggestion": null,
    "involvedCharacterIds": [101, 102],
    "refinedSummary": "정제된 표준 요약문"
  }
  ```

### `POST /intelligence/summary`

- **요청 (Request)**:
  ```json
  {
    "characterName": "캐릭터명",
    "episodeK": 5,
    "summaries": ["요약 1", "요약 2"]
  }
  ```
- **응답 (Response)**:
  ```json
  "통합 요약 결과"
  ```

## 💡 다시 읽어볼 내용 및 고려사항

1. **사용자 경험(UX) 최적화**
   - 위키 등록 즉시 응답을 주고, LLM 분석은 백그라운드에서 실행.
   - 분석 완료 시 "AI 제안 도착" 알림(WebSocket/SSE)을 주어 흐름의 끊김이 없도록 함.
   - UX 시나리오: 사용자가 글을 쓰고 등록 버튼을 누르면 즉시 "등록되었습니다. AI가 분석 중입니다..."라는 메시지와 함께 목록으로 이동하거나 상세 페이지를 보여줍니다.

2. **지능형 서비스의 독립성**
   - `intelligence-service`는 파이썬/FastAPI 등 AI 생태계에 최적화된 환경으로 전환 가능성을 열어두고 독립 서비스로 구축할 것.
   - 호출 비용이 비싸서 별도의 Rate Limit을 걸어야 할 수도 있습니다.
   - Q&A 서비스나 커뮤니티 서비스에서도 LLM 분석이 필요

3. **데이터 매핑 정밀도**
   - 캐릭터 DB와 드라마 정보를 LLM 프롬프트에 동적으로 주입하는 RAG 방식이 가장 효율적.

4. **안정성 (Fallback)**
   - AI 호출 불가능시: 단순 정규식 매칭 -> 기본값(OTHER/주인공전용) -> 수동 유역 순으로 방어막 구축.
   - 수동 유도: AI가 실패했다면 사용자에게 "AI 분석에 실패했습니다. 직접 인물을 태깅해 주시겠어요?"라고 정중히 부탁하는 UI를 띄웁니다.

5. **소통형 데이터 확장 전략 (Semantic OTHER)**
   - 초기 `PredicateCode` Enum은 범용적인 카테고리(v1) 위주로 구성.
   - LLM 분석 시 적절한 코드가 없으면 `OTHER`를 선택하되, `predicate_suggestion` 필드에 LLM이 판단한 원래의 영단어를 기록함 (예: `KIDNAPS`).
   - 추후 `OTHER`로 분류된 기록 중 빈도가 높은 키워드를 선별하여 정기적으로 정식 Enum으로 승격 및 배포함으로써 온톨로지를 점진적으로 확장함.
