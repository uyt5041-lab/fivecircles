# Event V2 고도화 통합 스펙 (V2 Plan + V2 고도화 Definition)

목적
- V2 구현 계획과 V2 고도화 정의를 하나의 스펙으로 정리한다.
- 'V2 고도화'는 기존 문서의 V2.5 범위를 동일하게 재명명한 것이다.
- V3 전 단계에서 predicate_code 기반 분석(Q20)과 문맥 인식 QA 컴포넌트를 오픈한다.

범위
- event-service (ontology/event domain)
- user-service (Flyway 테이블 분리)
- front (QA 공통 컴포넌트 및 Q1~Q15, Q20)

---

## 1) 핵심 규칙 (데이터 노출/게이트)

공통 게이트
- 모든 노출 쿼리에서 `episode_end <= :K` AND `source_status = 'APPROVED'`를 강제한다.
- Character 관련 조회도 반드시 event 조인을 통해 동일 게이트를 적용한다.

세이프 트래버설
- BFS/그래프 탐색은 확장 전에 게이트를 적용한다(중간 단계에서도 안전 그래프 밖으로 나가지 않음).

PRECEDES 방향 규칙
- PRECEDES는 '극중 진행축(노출/편집 순서)' 기준으로 `from=이전 사건`, `to=다음 사건`.
- 역방향 탐색은 `to_event_id` 기준으로 진행한다.

---

## 2) 데이터 모델 (V2 유지 + V2 고도화 보강)

event 테이블
- `predicate_code` (VARCHAR(30), 기본 `UNKNOWN`)
- `source_status` (VARCHAR(20), 기본 `APPROVED`)

event_character 테이블 (V2 고도화)
- `role` (VARCHAR(20), 기본 `INVOLVED`)
- `EventServiceImpl`의 하드코딩된 `PARTICIPANT`는 `INVOLVED`로 통일한다.

설명용 데이터
- REVEALS는 `event_reveal`에서만 유지하고, 설명/표시 용도로만 사용한다.

관계 타입 정책 (V2 고도화 유지)
- `event_relation.type`는 PRECEDES만 허용한다.
- 이유: Q7/Q9/Path는 극중 진행축(PRECEDES)만 사용한다.
- related는 저장 관계가 아니라 shared character 파생 규칙으로 정의한다.
- 자동 제안은 서로 다른 에피소드 간 PRECEDES만 생성 후보로 노출한다.
- 동일 에피소드 내 PRECEDES는 운영자 수동 큐레이션만 허용한다.

## 4) 환경/설정 (Flyway 충돌 방지)

문제
- 하나의 DB에서 여러 서비스가 동일한 Flyway history 테이블을 공유하면 충돌한다.

해결
- 서비스별 Flyway history 테이블을 분리한다.

설정
- event-service: `spring.flyway.table=flyway_schema_history_event`
- user-service: `spring.flyway.table=flyway_schema_history_user`

환경별 적용 가이드
- 로컬 개발: 각 서비스 `application.yml`에 위 설정을 기본값으로 둔다.
- docker/compose: 서비스별 `SPRING_FLYWAY_TABLE` 환경변수로 오버라이드한다.
- CI/테스트: 서비스별 독립 DB 또는 Flyway 테이블 분리 중 하나를 고정한다.

## 6) Query Type 정의 (20 Questions -> 6 Types)

Query Types
- CHARACTER_EVENTS: 인물 A가 관여한 사건
- EVENT_CHARACTERS: 사건 E에 등장한 인물
- CHARACTER_AND_CHARACTER_EVENTS: A와 B가 함께 나온 사건
- EVENT_CAUSES: 사건 E의 원인(이전 사건들, PRECEDES reverse)
- EVENT_EFFECTS: 사건 E의 결과(이후 사건들, PRECEDES forward)
- PATH_BETWEEN_CHARACTERS: A-B 최단 경로(이벤트/인물 혼합 BFS)

대표 매핑
- "A가 K화까지 관여한 사건" -> CHARACTER_EVENTS
- "사건 E 직전 사건들" -> EVENT_CAUSES
- "A와 B가 같이 등장한 사건" -> CHARACTER_AND_CHARACTER_EVENTS
- "A에서 B까지 연결 경로" -> PATH_BETWEEN_CHARACTERS
- "서사 분포(Q20)" -> CHARACTER_EVENTS + 클라이언트 집계

## 7) 쿼리 패턴 요약 (게이트 포함)

공통 조건
- `episode_end <= :K`
- `source_status = 'APPROVED'`

CHARACTER_EVENTS
- event + event_character 조인, predicate_code 필터 선택 가능.

EVENT_CHARACTERS
- event_character -> event 조인 후 게이트 적용.

CHARACTER_AND_CHARACTER_EVENTS
- event + event_character 2회 조인 (A, B).

EVENT_CAUSES / EVENT_EFFECTS
- event_relation PRECEDES 기반 BFS
- frontier 이벤트에 대해 양쪽 event 테이블 조인 후 게이트 적용.

PATH_BETWEEN_CHARACTERS
- character -> events (event_character)
- event -> event (event_relation)
- event -> character (event_character)
- 노드 출력은 `{node_type, node_id, hop_distance}` 형태.

## 8) Frontend 구현 (V2 고도화 QA)

공통 컴포넌트
- 문맥(Context)을 받아 질문을 제안하는 공통 버튼/드로어 기반.
- 고정 질문 버튼 테스트는 `/qa`에서 Q1~Q15를 배치한다.

구성
- `front/features/event/components/EventQAButton.tsx` (진입점)
- `front/features/event/components/EventQADrawer.tsx` (목록/결과)
- `front/features/event/components/widgets/` (질문별 위젯, Factory 패턴)

QA 집중 배치 (정식, `frontend.md` 기준)

원칙
- 질문 대부분은 /#/qa로 집중하고, 필수만 /#/dashboard, /#/timeline에 남긴다.
- Q20은 문맥(Context) QA 버튼으로 어디서든 호출 가능하게 한다.

페이지별 배치 + API (QA 집중 기준)

/#/qa
- Q2 인물 A·B 공동 등장 사건: api4 (coevents)
- Q8 같은 유형 사건 비교: api1 + predicateCode 비교
- Q13 A -> 사건 X -> B 경로: api10 + event X 검증

/#/dashboard
- Q1 인물 A 타임라인: api3 (getCharacterEvents)
- Q3 인물 C 사건 유형 필터: api3 + predicateCode
- Q6 인물 소속 변경 사건: api3 + predicateCode=AFFILIATION_CHANGE
- Q7 인물 사망/퇴장 사건: api3 + predicateCode=DEATH/EXIT
- Q14 인물 A 관련 인물: api9 (related characters)
- Q15 인물 A가 원인인 사건 연쇄: api3 -> api8 (또는 api6 PRECEDES)

/#/timeline
- Q4 사건 등장 인물: api5 (event characters)
- Q5 사건 유형별 모아보기: api1 + predicateCode
- Q9 특정 회차 범위 사건: api1 + fromEpisode/toEpisode
- Q10 사건 카테고리: api1 (predicateCode 표시)
- Q11 사건 원인(이전 사건): api7 (causes)
- Q12 사건 결과(이후 사건): api8 (effects)

축소/대체 UI (선택)
- /#/dashboard: Q2 공동 등장, Q13 경로는 요약 카드 + "QA에서 보기" CTA
- /#/timeline: Q8 비교 뷰는 제거하고 "QA 비교" CTA로 대체

추가 QA 이동 후보 (검토)
- Q9: 범위 필터 중심이라 QA 입력형으로도 충분함
- Q11/Q12: 원인/결과 그래프가 깊어질수록 QA가 적합함
- Q15: 영향 체인 상세는 QA에서 확장 뷰로 제공 가능

## 9) Q20 서사 분포 분석 (V2 고도화 핵심)

질문
- "인물 A의 서사가 어떤 사건 카테고리에 가장 많이 걸쳐 있나?"

처리 흐름
- 캐릭터 문맥에서 "분석하기" 노출
- `eventV2Api.getCharacterEvents` 호출
- `predicateCode`별 카운트 집계 후 상위 N개 출력
- `PredicateCode` 설명과 함께 분포 리스트/차트 표시
