# 프로젝트별 에이전트 지휘 플랜

> 작성일: 2025-01-16
> 목적: 멀티 에이전트 협업 시스템 설계 및 확장 가이드

---

## 1. 배경

### 문제
- MCP 서버 에이전트들이 동시에 작업 시 충돌 발생
- Gemini API 에러: "function response parts != function call parts"
- 여러 에이전트가 같은 MCP 서버 공유 시 응답 매칭 오류

### 해결 원칙
1. 에이전트별 MCP 분리 (충돌 방지)
2. 공유 파일로 작업 내용 공유 (sync.md, queue.json)
3. 락(Lock) 메커니즘으로 동시 수정 방지
4. Debate 프로토콜로 충돌 해결

---

## 2. 현재 구조 (소규모 - 팀원 C 단독)

### 에이전트 역할

| Alias | Agent | 역할 | 담당 |
|-------|-------|------|------|
| `agent-plan` | Gemini | Planner (조율자) | 전체 조율, 기획, 태스크 분배 |
| `agent-code` | Claude | Coder (구현자) | event, spoiler-policy, qa 서비스 코딩 |
| `agent-codex` | Codex | Ops (운영자) | Deploy, Git, 문서 편집 |
| `agent-review` | Claude | Reviewer (검토자) | 코드 리뷰, 테스트 |

### 지휘 체계

```
사용자
  ↓
Planner (Gemini) ─── 모든 지시는 Planner를 통해
  ├── Coder (Claude) ─── 코드 구현
  ├── Ops (Codex) ───── 배포/Git/문서
  └── Reviewer (Claude) ─ 리뷰/테스트
```

### 작업 흐름

```
1. 사용자 → Planner에게 요청
2. Planner → 태스크 분해 → queue.json에 등록
3. Planner → 각 에이전트에게 지시
4. 에이전트 → 작업 전 sync.md 확인, 락 획득
5. 에이전트 → 작업 수행
6. 에이전트 → 락 해제, sync.md 업데이트
7. Planner → 결과 확인, 다음 태스크 진행
```

### 병렬 작업

- 서로 다른 서비스는 동시 작업 가능
- 같은 서비스/파일은 락으로 순차 처리
- Planner가 기획하는 동안 Coder는 이전 태스크 구현 가능

## 3. 확장 구조 A: 계층적 에이전트 (서비스별 팀)

프로젝트가 커지면 서비스별로 팀을 구성

### 구조

```
Master Planner (Gemini)
│
├── event-service Team
│   ├── Sub-Planner (Claude)
│   ├── Coder 1 (Claude)
│   ├── Coder 2 (Codex)
│   └── Reviewer (Claude)
│
├── spoiler-policy-service Team
│   ├── Sub-Planner (Claude)
│   ├── Coder 1
│   └── Reviewer
│
├── qa-service Team
│   └── ...
│
└── Ops Team (공통)
    ├── Deploy Ops
    └── Git Ops
```

### 필요한 변경

1. **Config 분리**
```
fivecircles/agent/configs/
├── master-planner.json
├── event-service/
│   ├── sub-planner.json
│   ├── coder-1.json
│   └── reviewer.json
├── spoiler-policy-service/
│   └── ...
```

2. **서비스별 sync/queue 분리**
```
fivecircles/agent/
├── sync.md              # Master 레벨
├── queue.json           # Master 레벨
├── event-service/
│   ├── sync.md          # 서비스 레벨
│   └── queue.json
```

3. **서비스별 alias**
```bash
alias agent-event-plan='...'
alias agent-event-code='...'
```

## 4. 확장 구조 B: 팀 단위 분리 (재귀적 사이클)

더 큰 프로젝트에서 팀원 A, B, C가 각각 독립적으로 작업

### 구조

```
Agent A ──→ 내부에서 Plan → Code → Deploy → Review 사이클 반복
            담당: api-gateway, auth-service, user-service, admin-service

Agent B ──→ 내부에서 Plan → Code → Deploy → Review 사이클 반복
            담당: drama-service, character-service, wiki-service

Agent C ──→ 내부에서 Plan → Code → Deploy → Review 사이클 반복
            담당: event-service, spoiler-policy-service, qa-service
```

### 특징

- **한 에이전트가 모든 역할을 순차적으로 수행**
- 내부적으로 fivecircles 사이클 반복
- 팀 간 독립성 최대화
- 컨텍스트 유지 (한 에이전트가 전체 흐름 파악)

### 지시 예시

```
"너는 팀원 C 전담 에이전트야.
fivecircles 사이클대로:
1. [Plan] 요구사항 분석, 태스크 분해
2. [Code] 구현
3. [Deploy] 배포
4. [Review] 테스트/검증
5. [Maintenance] 피드백 반영
이 사이클을 반복해서 event-service, spoiler-policy-service, qa-service를 완성해."
```

### Alias 예시

```bash
alias agent-team-a='gemini -i "팀A 전담. api-gateway, auth, user, admin 담당. fivecircles 사이클 반복 실행."'
alias agent-team-b='claude --append-system-prompt "팀B 전담. drama, character, wiki 담당. fivecircles 사이클 반복 실행."'
alias agent-team-c='codex "팀C 전담. event, spoiler-policy, qa 담당. fivecircles 사이클 반복 실행."'
```

### 비교

| 구조 A (계층적) | 구조 B (팀 단위) |
|----------------|-----------------|
| 병렬 작업 극대화 | 팀 간 독립성 극대화 |
| 에이전트 간 통신 복잡 | 컨텍스트 유지 용이 |
| 세분화된 역할 | 한 에이전트가 전체 사이클 |
| 대규모 병렬 개발에 적합 | 팀 분리 개발에 적합 |

## 8. 핵심 원칙

1. **모든 지시는 Planner를 통해** - 혼란 방지
2. **작업 전 sync.md 확인** - 현황 파악
3. **락 획득 후 작업** - 충돌 방지
4. **fivecircles 사이클 준수** - Requirements → Design → Implementation → Test → Maintenance
5. **specs/가 Source of Truth** - 스펙 기반 개발
